# 01 仕様書 — study-gcp-feature-store-offline

Vertex AI Feature Store の **Offline / BigQuery 連携**を技術学習するための不動産検索向けサンプルプロジェクト仕様。

本プロジェクトでは、`feature_emb_a.csv` / `feature_emb_b.csv` を起点に BigQuery へ特徴量データを取り込み、Vertex AI Feature Store の Feature Group / Feature として登録する。
その後、Python batch から **オフライン特徴量として取得**し、取得結果をログに書き出すところまでを検証対象とする。

重要方針として、**Feature Store は使うが、Feature Store Online / Online Store / Feature View / Feature View sync / Redis 連携は一切扱わない**。
オンライン低レイテンシ配信は既に Redis で対応済みであるため、Feature Store Online は今回の ROI 対象外とする。

この仕様でいう「Feature Store を使う」とは、**Feature Group / Feature を Feature Registry metadata として使う**ことを指す。
Feature Group の BigQuery source と Feature 一覧を取得し、その metadata に基づいて BigQuery offline source を読む。
Feature View / Online Store / sync / `fetchFeatureValues` は Online serving 側の概念なので、本プロジェクトでは禁止する。

Feature Store REST API は使う。ただし用途は registry / metadata 取得に限定する。
実データの取得は BigQuery API で行う。

## 1. 目的・学習ゴール

不動産物件のサンプル特徴量 `feature_emb_a.csv` / `feature_emb_b.csv` を題材に、以下の責務分離を実機で理解する。

* **feature_emb_a.csv / feature_emb_b.csv**

  * ローカルまたは GCS 上の特徴量入力ファイル
  * 学習用の固定サンプルデータ

* **BigQuery**

  * 特徴量データの実体
  * SQL 確認・集計・バッチ取得の中心
  * Feature Store Offline の参照元

* **Vertex AI Feature Store**

  * 特徴量の管理・メタデータ・参照レイヤー
  * 今回は Offline 利用に限定する

* **Feature Group**

  * BigQuery 特徴量テーブルを Feature Store に登録する単位
  * Entity ID、Feature 定義、スキーマ管理を担う

* **Feature**

  * BigQuery 上の特徴量カラムを Feature Store 上の Feature として登録する単位

* **Python batch**

  * オフライン特徴量を取得し、ログへ書き出す検証処理
  * 本番推論 API ではなく、batch / downstream 利用の確認を目的とする

## 4. 採用しない構成

今回、以下は明示的に採用しない。

```text
Feature View
Feature View sync
Online Store
Feature Store Online fetchFeatureValues
Redis 書き込み
Redis 読み込み
Redis 置き換え
低レイテンシ API serving
Endpoint 推論 API
リアルタイム配信
```

以下の実装が入った場合は、この仕様違反として扱う。

```text
Feature View を作成する
Online Store を作成する
Feature View sync API を呼ぶ
fetchFeatureValues を呼ぶ
Redis client / Redis 環境変数 / Redis read-write を追加する
低レイテンシ serving / 推論 Endpoint を追加する
```

理由は、現行システムではオンライン低レイテンシ配信を Redis が既に担っており、Feature Store Online を追加しても ROI が薄いからである。
今回の Feature Store 導入価値は、オンライン配信ではなく、**BigQuery 上の特徴量を Feature Store の Feature Group / Feature として管理し、オフライン利用・再利用・監査性を高めること**に限定する。

### 4.1 今回 Feature Store で使うもの

今回使う Feature Store の範囲は次だけである。

```text
Feature Group
Feature
Feature Group の BigQuery source / BigQuery View
Feature Registry metadata
```

責務分担は次の通り。

| レイヤー | 責務 |
|---|---|
| Feature Group | どの BigQuery View が正しい特徴量 source かを示す |
| Feature | どの column が Feature として公開されているかを示す |
| BigQuery | offline feature values の物理保存と batch read |
| Redis | 既存 online low latency serving。今回の実装では触らない |

つまり、**Feature Store は使う。Feature Store Online は使わない。Feature View は Online Store 側なので使わない。使うのは Feature Group / Feature だけ。**

### 4.2 Feature Store REST API の利用範囲

Feature Store REST API は使うが、Online 系 API は使わない。

使う API:

```text
GET  /v1/projects/{project}/locations/{region}/featureGroups/{feature_group}
GET  /v1/projects/{project}/locations/{region}/featureGroups/{feature_group}/features
```

用途:

```text
Feature Group の BigQuery source URI を取得する
Feature Group の Entity ID column を取得する
Feature Group 配下の Feature ID 一覧を取得する
```

使わない API:

```text
featureViews.*
onlineStores.*
featureViews.sync
fetchFeatureValues
```

整理すると、次の責務分担とする。

```text
Feature Store REST API = registry / metadata 取得
BigQuery API           = offline feature values 取得
Online Store / Feature View / sync = 今回は完全禁止
```

## 5. スキーマ

### 入力ファイル: `feature_emb_a.csv` / `feature_emb_b.csv`

埋め込みソース別にファイルを分割する。各ファイルに `embedding_source` 列を持ちリネージュを明示する。

`data/feature_emb_a.csv`（テキスト属性モデル由来スコア）:

```csv
event_date,feature_timestamp,property_id,embedding_source,rent,walk_min,age_years,area_m2,emb_a_ctr,emb_a_fav_rate,emb_a_semantic_score
2026-06-02,2026-06-02T00:00:00+09:00,p001,emb_a,85000,7,12,32.5,0.1200,0.0300,0.72
2026-06-02,2026-06-02T00:00:00+09:00,p002,emb_a,92000,5,8,28.1,0.1400,0.0400,0.68
```

`data/feature_emb_b.csv`（行動ログモデル由来スコア）:

```csv
event_date,feature_timestamp,property_id,embedding_source,rent,walk_min,age_years,area_m2,emb_b_inquiry_rate,emb_b_collab_score,emb_b_engagement
2026-06-02,2026-06-02T00:00:00+09:00,p001,emb_b,85000,7,12,32.5,0.0100,0.65,0.40
2026-06-02,2026-06-02T00:00:00+09:00,p002,emb_b,92000,5,8,28.1,0.0150,0.70,0.45
```

### BigQuery: `feature_mart.property_features_daily`

| 列 | 型 | mode | 区分 |
|---|---|---|---|
| `event_date` | DATE | REQUIRED | partition |
| `feature_timestamp` | TIMESTAMP | NULLABLE | feature-time 列 |
| `property_id` | STRING | REQUIRED | Entity ID / clustering key 1 |
| `embedding_source` | STRING | REQUIRED | `'emb_a'` or `'emb_b'` / clustering key 2 / **lineage 列** |
| `rent` | INT64 | NULLABLE | Feature (共通) |
| `walk_min` | INT64 | NULLABLE | Feature (共通) |
| `age_years` | INT64 | NULLABLE | Feature (共通) |
| `area_m2` | FLOAT64 | NULLABLE | Feature (共通) |
| `emb_a_ctr` | FLOAT64 | NULLABLE | emb_a 動的スコア: テキスト属性モデルCTR |
| `emb_a_fav_rate` | FLOAT64 | NULLABLE | emb_a 動的スコア: テキスト属性お気に入り率 |
| `emb_a_semantic_score` | FLOAT64 | NULLABLE | emb_a 固有: セマンティック類似スコア |
| `emb_b_inquiry_rate` | FLOAT64 | NULLABLE | emb_b 動的スコア: 行動ログ問い合わせ率 |
| `emb_b_collab_score` | FLOAT64 | NULLABLE | emb_b 動的スコア: 協調フィルタリングスコア |
| `emb_b_engagement` | FLOAT64 | NULLABLE | emb_b 固有: エンゲージメントスコア |

**命名規則**: 動的スコアは `emb_a_*` / `emb_b_*` プレフィックスで流入元を明示。
共通 Feature (rent/walk_min/age_years/area_m2) は両 embedding_source 行ともに値を持つ。
`embedding_source = 'emb_a'` の行は `emb_b_*` が NULL、逆も同様。

### BQ View → Feature Group 対応

Feature Store へは `embedding_source` 別の BQ View 経由で Feature Group を 2 つ登録する。

| BQ View | Feature Group | Features |
|---|---|---|
| `feature_mart.v_property_features_emb_a` | `fg_property_emb_a` | rent, walk_min, age_years, area_m2, emb_a_ctr, emb_a_fav_rate, emb_a_semantic_score |
| `feature_mart.v_property_features_emb_b` | `fg_property_emb_b` | rent, walk_min, age_years, area_m2, emb_b_inquiry_rate, emb_b_collab_score, emb_b_engagement |

`property_id` は各 Feature Group の Entity ID。
`event_date` / `feature_timestamp` / `embedding_source` は Feature 登録対象外とする。

## 6. コマンド仕様

Cloud Run Jobs またはローカル実行で、以下のコマンドを用意する。

```bash
python -m app.main seed-csv
python -m app.main load-bq
python -m app.main register-fs
python -m app.main batch-read-offline
```

### `seed-csv`

ローカルまたは GCS に `feature_emb_a.csv` / `feature_emb_b.csv` を作成する。

目的:

```text
固定サンプル特徴量データをソース別に 2 ファイル用意する
```

### `load-bq`

`feature_emb_a.csv` と `feature_emb_b.csv` を BigQuery の `feature_mart.property_features_daily` にロードする。

目的:

```text
Feature Store Offline の実体となる BigQuery テーブルを作成・更新する
emb_a / emb_b の行が同一テーブルに入り embedding_source でリネージュが識別できること
```

### `register-fs`

BQ View 経由で embedding_source 別に Vertex AI Feature Store の Feature Group / Feature を登録する。

目的:

```text
BQ View を Feature Store の管理対象とし、embedding ソースごとにリネージュを持つ Feature Group を作る
```

作成対象:

```text
Feature Group: fg_property_emb_a  (BQ View: feature_mart.v_property_features_emb_a)
  Features: rent, walk_min, age_years, area_m2,
            emb_a_ctr, emb_a_fav_rate, emb_a_semantic_score

Feature Group: fg_property_emb_b  (BQ View: feature_mart.v_property_features_emb_b)
  Features: rent, walk_min, age_years, area_m2,
            emb_b_inquiry_rate, emb_b_collab_score, emb_b_engagement
```

作成しない対象:

```text
Feature View
Online Store
sync job
fetchFeatureValues
Redis
```

### `batch-read-offline`

Cloud Run Job として実行し、Feature Store の Feature Group / Feature metadata を経由して emb_a / emb_b それぞれの BigQuery offline source を解決し、特徴量を取得してログに書き出す。

目的:

```text
Feature Store の Feature Group / Feature として管理された BigQuery 特徴量を
downstream batch で取得・利用できることを確認する
emb_a / emb_b 別に取得し、リネージュが維持されていることを確認する
```

必須処理:

```text
Feature Group を GET する
Feature Group の bigQuerySource.inputUri から BigQuery View を解決する
Feature 一覧を LIST する
Feature ID 一覧から SELECT column を組み立てる
BigQuery API で offline read を実行する
stdout / GCS JSONL に出力する
```

実装上の重要制約:

```text
Python に BigQuery table/view 名を固定で直書きしない
Python に feature column 名を固定で直書きしない
Feature Group の BigQuery source を変更したら batch の取得元も変わること
Feature の追加・削除が Feature LIST の結果を通じて SELECT column に反映されること
```

禁止処理:

```text
Feature View を参照しない
Online Store を参照しない
Feature View sync を実行しない
fetchFeatureValues を呼ばない
Redis を読まない / 書かない
低レイテンシ serving として実装しない
```

実行形態: **Cloud Run Job**

出力先:

| 出力先 | 内容 |
|---|---|
| stdout (Cloud Logging) | 1 行 1 property のログ (常時) |
| GCS JSONL | 同内容をファイル書き出し (Cloud Logging が見づらい場合の代替参照用) |

GCS パス:

```text
gs://mlops-dev-a-feature-offline-asia-northeast1/offline-batch/{YYYYMMDD}/emb_a/result.jsonl
gs://mlops-dev-a-feature-offline-asia-northeast1/offline-batch/{YYYYMMDD}/emb_b/result.jsonl
```

stdout ログ出力例:

```text
[offline-feature][emb_a] property_id=p001 rent=85000 walk_min=7 age_years=12 area_m2=32.5 emb_a_ctr=0.12 emb_a_fav_rate=0.03 emb_a_semantic_score=0.72
[offline-feature][emb_b] property_id=p001 rent=85000 walk_min=7 age_years=12 area_m2=32.5 emb_b_inquiry_rate=0.01 emb_b_collab_score=0.65 emb_b_engagement=0.40
```

## 7. Python batch の責務

`batch-read-offline` はオンライン serving ではなく Cloud Run Job として実行する。
Feature Store Online の値取得 API ではなく、Feature Group / Feature registry を読み、その registry が示す BigQuery source から offline read する。

責務は以下に限定する。

```text
Feature Group を GET して BigQuery source URI を取得する
Feature 一覧を LIST して取得対象 column を決める
Feature Group の BigQuery source に対して対象日付の BigQuery query を実行する
property_id 単位で特徴量を整形する
取得結果を stdout（Cloud Logging）に書き出す
同内容を GCS に JSONL 形式で書き出す（Cloud Logging が見づらい場合の代替参照用）
```

取得 SQL は固定 SQL を手書きで持つのではなく、Feature Group / Feature metadata から組み立てる。

Feature Store REST API コール順:

```text
1. GET .../featureGroups/{fg_id}
       → bigQuery.bigQuerySource.inputUri  "bq://project.dataset.view"
       → bigQuery.entityIdColumns          ["property_id"]

2. GET .../featureGroups/{fg_id}/features
       → features[].name から Feature ID 一覧を抽出
         例: ["rent", "walk_min", "age_years", ..., "emb_a_ctr", ...]

3. SELECT {entity_id_cols} + {feature_ids}
   FROM `{bq_ref derived from inputUri}`
   WHERE event_date = CURRENT_DATE(...)
```

Feature Group が存在しない (404) 場合はバッチを即時失敗させる。
Feature が未登録 (空リスト) の場合も同様に失敗させる。
Python 側に BQ View 名や Feature column 名を固定配列として持たせ、Feature Store REST API の結果を使わずに SQL を作る実装は禁止する。

生成される SQL のイメージは次の通り。

取得 SQL 生成例 (emb_a):

```sql
SELECT
  property_id,
  rent,
  walk_min,
  age_years,
  area_m2,
  emb_a_ctr,
  emb_a_fav_rate,
  emb_a_semantic_score
FROM `mlops-dev-a.feature_mart.v_property_features_emb_a`
WHERE event_date = CURRENT_DATE("Asia/Tokyo")
ORDER BY property_id
```

取得 SQL 生成例 (emb_b):

```sql
SELECT
  property_id,
  rent,
  walk_min,
  age_years,
  area_m2,
  emb_b_inquiry_rate,
  emb_b_collab_score,
  emb_b_engagement
FROM `mlops-dev-a.feature_mart.v_property_features_emb_b`
WHERE event_date = CURRENT_DATE("Asia/Tokyo")
ORDER BY property_id
```

## 10. `app.main` コマンド案

```python
"""Cloud Run job / local batch エントリポイント。引数でコマンドを分岐する。

python -m app.main seed-csv            # feature_emb_a.csv / feature_emb_b.csv を作成
python -m app.main load-bq             # feature_emb_a.csv / feature_emb_b.csv を BigQuery へロード
python -m app.main register-fs         # BigQuery テーブルを Feature Group / Feature として登録
python -m app.main batch-read-offline  # Feature Group / Feature metadata 経由で BQ offline read → ログ出力

注意:
- Feature View は作成しない
- Online Store は作成しない
- Feature View sync は実行しない
- fetchFeatureValues は呼ばない
- Redis は触らない
"""

from __future__ import annotations

import sys
from collections.abc import Callable

from app.batch import read_offline
from app.data import load_bq, seed_csv
from app.feature_store import register

COMMANDS: dict[str, Callable[[], None]] = {
    "seed-csv": seed_csv.run,
    "load-bq": load_bq.run,
    "register-fs": register.run,
    "batch-read-offline": read_offline.run,
}


def main(argv: list[str]) -> int:
    if len(argv) < 2:
        print(f"usage: python -m app.main <{'|'.join(COMMANDS)}>", file=sys.stderr)
        return 2

    command = argv[1]
    handler = COMMANDS.get(command)

    if handler is None:
        print(
            f"[error] unknown command: {command} (expected {'|'.join(COMMANDS)})",
            file=sys.stderr,
        )
        return 2

    handler()
    return 0


if __name__ == "__main__":
    raise SystemExit(main(sys.argv))
```

```text
Web UI
認証付き REST API
```

## 13. 判断理由

Feature Store Online は低レイテンシ配信を目的とするが、本プロジェクトでは既に Redis がその責務を満たしている。
そのため、Feature Store Online を追加すると、以下の問題が発生する。

```text
既存 Redis 構成との責務重複
同期経路の増加
障害点の増加
リージョン設計の複雑化
運用コスト増
学習目的のブレ
```

今回の Feature Store 導入価値は、オンライン配信ではなく、BigQuery 上の特徴量を Feature Store の Feature Group / Feature として管理し、オフライン batch で取得できる状態を確認することにある。

## 14. 最終ゴール

最終的に、以下の流れが成功すれば完了とする。

```text
feature_emb_a.csv / feature_emb_b.csv
  → BigQuery (embedding_source でリネージュ記録)
  → BQ View emb_a / BQ View emb_b
  → Vertex AI Feature Store Feature Group × 2 / Feature × 7 × 2
  → Python batch (Cloud Run Job)
      Feature Group GET / Feature LIST
      bigQuerySource.inputUri から BQ View 解決
      Feature ID 一覧から SELECT column 生成
      BigQuery offline read
  → stdout ログ + GCS JSONL 書き出し
```

成功条件:

```text
BigQuery に emb_a / emb_b 両ソースの特徴量が投入されている
BQ View が embedding_source で正しくフィルタできる
Feature Group fg_property_emb_a / fg_property_emb_b が作成されている
Python batch が Feature Group を GET している
Python batch が Feature 一覧を LIST している
Python batch が Feature Group の bigQuerySource.inputUri から BQ View を解決している
Python batch が Feature ID 一覧から SELECT column を生成している
Python batch が BQ View から対象日の特徴量を offline read できる
stdout に property_id ごとの特徴量が出力される
GCS に result.jsonl が書き出される
Redis / Feature Store Online / Online Store / Feature View / Feature View sync / fetchFeatureValues を一切使っていない
```

破綻条件:

```text
Python に BQ table/view 名を固定で直書きしている
Python に Feature column 名を固定で直書きしている
Feature Group を参照せずに BigQuery を読んでいる
Feature 一覧を参照せずに BigQuery を読んでいる
Feature Group が消えても batch が成功してしまう
Feature が消えても batch が検知できない
Feature View を作っている
Online Store を作っている
sync を実行している
fetchFeatureValues を呼んでいる
Redis client / Redis env が入っている
```
